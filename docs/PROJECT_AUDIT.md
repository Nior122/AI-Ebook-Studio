# AI Ebook Studio — Project Audit

- **Audit date:** 2026-10-05
- **Repository baseline:** `48267ae86e6667df47479c83c8c99493611c7b51` (`master`)
- **Scope:** frontend, backend, persistence/migrations, authentication, AI and image providers, generation workflows, exports, tests, environment, and deployment configuration. This audit describes observed code and executed checks; it does not infer production readiness from route/file presence.

## Executive summary

This is a substantial, partially implemented application—not an empty scaffold. It contains a Next.js/TypeScript frontend, FastAPI/SQLAlchemy backend, a linear Alembic history, API and component tests, provider adapters, a staged chapter-generation pipeline, project workspace, editing suggestions, exports, validation, image tables, and deployment templates.

The main risk is **workflow integrity**. The visible one-click path does not yet deliver a reliably on-topic, realistically sized book. In a real API-level, no-credential run (registered a user, submitted *AI Tools for Teachers*, requested 3,000 words across 3 chapters, waited for the job, and inspected persisted chapter content), the job reached `COMPLETED`, but the book had `needs_review`, reported 24,038 actual words, used the offline fallback for 23 generation calls, and emitted repeated generic “Foundations” / “The book” prose rather than teacher-specific content. This is a concrete quality failure—not a claim based on a missing endpoint. The application test suite accepted that run because its generation assertions check that chapters exist and the job terminates, not that content meets topic or length standards.

A second data-safety defect is more urgent: both synchronous and background translation paths replace the source chapters' `content` in place. Translation history records languages and status, but not a separate translated manuscript. The current help text explicitly advises users to make a backup before translating. This conflicts with the required non-destructive translation workflow.

A third integration hazard is that one logical book is represented by both `books` and `bw_books`. The relation is stored in `books.metadata_json.writing_book_id`; some code uses the project-level `Book.id`, while export/KDP use the writing-book id. Formatting settings are written against the former but read against the latter, and the automatic image planner reads a legacy structured document that the current writing pipeline does not populate.

**Current conclusion:** core foundations are present; no end-to-end publishing workflow is verified complete. Prioritize preserving source content and repairing book-quality gates before expanding feature surface area.

### Generation defect reproduction

- Request: title **AI Tools for Teachers**, teacher-beginner audience, classroom-use description, 3 chapters, 3,000 target words.
- Provider: configured as OpenRouter, but no key was available; `AIService` routed 23 calls to `LocalProvider`.
- Observed response: job status `COMPLETED`; book status `needs_review`; 3 body chapters plus introduction and conclusion; 24,038 actual words (about 8× the requested total).
- Persisted samples began with `# Foundations` and prose such as “The book starts with a clear map”; chapter content repeated generic template paragraphs rather than the specified classroom use cases.
- Chapter validation returned no usable scores and the pipeline accepted chapters as-is (`validation_unavailable=True`). The final quality report did warn about offline fallback, but job completion and content length/topic checks were insufficiently gated.

## Architecture and documentation findings

- Existing documentation conflicts with the current code. The root README describes a completed end-to-end workflow; `backend/README.md` still says writing/editing/export are not implemented; older product docs say features are future work. Treat code and the tests above as the current state, then update docs as features are actually verified.
- The image engine's automatic planner uses the relational structured-document hierarchy (`models.document`) and the project-level `Book`; the main writing engine assembles markdown content into `WritingChapter`. They are not currently one shared manuscript representation.
- The current page-size setup writes one `BookSettings` row against the project-level `Book` while export and KDP query by `WritingBook` ID. This is a concrete cross-module key mismatch.
- No commit/push/deployment was performed during the audit. No external provider credential or user data was accessed.

## Audit disposition

The audit identifies a usable foundation, not a finished ebook-production product. Follow `docs/IMPLEMENTATION_ROADMAP.md` in priority order. Re-run this audit after implementation; do not promote a row to `COMPLETE` from compilation or HTTP 200 alone.

## Implementation follow-up — 2026-10-05

The audit above is the baseline snapshot at commit `48267ae86e6667df47479c83c8c99493611c7b51`; the following is a dated update, not a claim that the product is complete:

- **Translation data safety:** source-preserving translated editions are implemented for synchronous and background flows, with retry/source-revision checks and separate target chapter content. Regression coverage now verifies the source manuscript remains unchanged and another user cannot read an edition. The studio panel has edition history/reopen/resume behavior. PostgreSQL upgrade on populated data, cancellation, translation export/side-by-side review, and a real authenticated browser workflow remain unverified.
- **Book identity/settings:** a canonical nullable `WritingBook.project_book_id` foreign key now replaces title/order selection in autosave, generation resumption, and job/project resolution. Unambiguous legacy metadata links are backfilled; ambiguous links remain unset rather than being guessed. Export and KDP now load formatting settings through the canonical link. The production regression sets 8×10 with a 1.25-inch left margin, confirms KDP sees 8×10, opens the produced DOCX with `python-docx`, and checks page dimensions/margin. It also exercises PDF output after mapping common UI font names to ReportLab-compatible families. SQLite upgrade/backfill checks passed; PostgreSQL and operator reporting for skipped/ambiguous links are not verified.
